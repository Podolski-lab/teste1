# Reconciliation — Architecture Spine vs PRD/UX/Brief-addendum

## Gaps found

- **FR-6 reschedule has no follow-through path.** AD-3 records a terminal `reagendado` status and the ERD carries a `rescheduled_to` field, but nothing in AD-1/AD-3/AD-4 or the infra layer (`CalendarClient`) specifies writing the new time back to Google Calendar, or otherwise creating a future `TaskInstance` the Poller can find. AD-3 fixes `task_id = {calendar_event_id}#{date}`, i.e. every task instance is derived strictly from an existing calendar event — there is no defined mechanism for a rescheduled task to ever re-enter the reminder/checkpoint loop (FR-1/FR-3) at its new time. As specced, "tudo bem, que tal amanhã no mesmo horário?" (Flow 1 climax, UX) is accepted verbally and recorded, but nothing will actually remind the user tomorrow. This directly undercuts SM-2 (PRD's primary success metric), which is exactly the scenario this flow exists for.

- **FR-12 (on-demand weekly summary) is misattributed and its interaction path is undrawn.** The Capability Map puts FR-12 under "Rotina de horário fixo → Custom Task ... governed by AD-4," but per EXPERIENCE.md (Intent table, Flow 3) FR-12 is triggered by the user directly invoking the Skill ("sempre — sob demanda"), with no Routine, no Custom Task, and no Poller involvement — a completely different mechanism from the proactive reminder/checkpoint/weekly-summary paths AD-4 exists to govern. The Structural Seed's container-flow diagram has no arrow for a direct `Device → SkillFn` invocation independent of `CustomTask`/`TriggerAPI`/`Routine`; this interaction mode has no accurate architectural home.

- **Manual Alexa Routine setup (identified in `.memlog.md`) never made it into the spine document itself.** `.memlog.md` line 10 explicitly flags: "*Requer setup manual do usuário no app da Alexa (criar as Rotinas uma vez) - gap novo em relação ao PRD/UX*". `ARCHITECTURE-SPINE.md` has no ASSUMPTION or Deferred entry recording this. At minimum four Routines must be hand-created in the Alexa app (reminder-trigger routine, checkpoint-trigger routine, Friday-18h routine, Sunday-20h routine) before anything fires — a reader of only the finalized spine has no way to know this prerequisite exists.

- **Silence/no-response persistence for FR-4/FR-5 has no named writer.** UX's `AwaitingCheckpointRetry → SessionEnded` (silence twice → end, no further attempt) needs `sem_resposta` written to `TaskInstance.status` for the weekly tally (FR-5/FR-9) to be accurate. On real user silence, Alexa ends the session itself (`SessionEndedRequest` after reprompt exhaustion) rather than invoking a normal intent handler with data to act on. Neither AD-2 nor the source tree's `skill.ts` names a `SessionEndedRequestHandler` responsible for calling `transitionTaskStatus(..., 'sem_resposta')` in this path — without it, the FSM's `sem_resposta` branch has no confirmed writer.

- **Who edits `PillarConfig` is inconsistent between `.memlog.md` and the PRD.** PRD FR-11 states the pillar/purpose association "é feita manualmente pelo próprio usuário diretamente no backend." `.memlog.md` line 22 instead says the table is "editada manualmente por Claude via AWS CLI/console" — i.e., the implementing agent, not the user, performs ongoing edits. `ARCHITECTURE-SPINE.md`'s own AD-5 wording ("editada fora da aplicação") is neutral enough to avoid the contradiction directly, but the decision trail behind it conflicts with FR-11's framing of this as user-owned, ongoing config — worth resolving explicitly before build, since a hobby single-user project can't rely on Claude making ad hoc edits every time a new recurring calendar event needs a pillar.

## Confirmed coverage

- FR-1/FR-2 (reminder + purpose reconnection), FR-3 (checkpoint, session-based sim/não), FR-5 (response recorded to `TaskInstance`), FR-7/FR-8 (Friday 18h ask + Sunday 20h retry via two fixed-time Routines), FR-9/FR-10 (weekly summary content/closing), FR-11 (PillarConfig as data), NFR-1 (free-tier stack), NFR-3 (tone centralized in domain) — all have a clear home in the Capability → Architecture Map.
- AD-4's "exactly two Custom Triggers" (`reminder-trigger`, `checkpoint-trigger`) matches the UX's two proactive intents per task (`ReminderDelivery`, `CheckpointQuestion`); the reschedule sub-dialog and the checkpoint reprompt both stay inside the single session a Custom Task opens, so no third trigger is needed — traced correctly.
- Barge-in (UX Interaction Primitives) is a platform default for Echo devices and isn't contradicted or blocked by anything in the spine.
- Tier-3/custom-Lambda-Skill decision, Node.js/ASK SDK choice, and the reminder-trigger vs fixed-Routine split are all consistent with the brief addendum's technical research (native Alexa↔Calendar integration's lack of pillar tags/instant sync, Custom Triggers requiring "algum nível técnico").
